# dzen: контракт CLI

Статус: заморожен 2026-11-09. Основание: [сводка исследования](research/to-cli-synthesis.md) и отчёты 01–06. Непроверенное вживую перечислено в разделе «Не подтверждено вживую».

`dzen` управляет статьями и комментариями канала Дзена из терминала: для агента написать статью здесь так же просто, как написать Markdown-файл.

```text
dzen [global flags] <command> [args]
```

Текст help, сообщения и коды ошибок на английском. Документация на русском.

## Команды

### Статьи как файлы

| Команда | Что делает | Сеть |
|---|---|---|
| `dzen push <file> [--dry-run] [--force] [--yes]` | Нет `dzen.publication_id`: создаёт черновик и записывает ID в файл. Есть: обновляет. По умолчанию сохраняет, а не публикует. | да |
| `dzen pull <id\|url> [--dir DIR] [--force]` | Записывает `<dir>/<slug>.md` и снимок `.dzen/<publication_id>.json`. Отказывается перезаписать несохранённые локальные правки без `--force`. | да |
| `dzen diff <file> [--remote]` | Без флага: файл против снимка, сети нет. С `--remote`: снимок против сервера. | только `--remote` |
| `dzen status [file\|id]` | Статус рабочей копии (`clean`, `modified`, `conflict`) и статус на сервере. | да |
| `dzen publish <file\|id> [--at TIME] [--wait DUR] [--dry-run] [--force] [--yes]` | Публикует сейчас или планирует на `TIME` (RFC 3339, окно 1 час — 365 дней). Повторный вызов с новым `--at` переносит дату. Вызов без `--at` для запланированной статьи публикует её немедленно. Если файл отличается от снимка, изменения уходят в той же операции. | да |

### Управление

| Команда | Что делает |
|---|---|
| `dzen draft list [--limit N]` | Черновики, всегда live. |
| `dzen draft show <id> [--format md\|json]` | Черновик без записи файла. |
| `dzen draft delete <id> [--yes]` | Необратимо. |
| `dzen article list [--state published\|pending] [--limit N]` | Публикации, по умолчанию опубликованные, новые первыми, 100 штук. `pending` это запланированные. `data.has_more` = `true`, если `--limit` обрезал список. У элемента есть `type` (`article`, `brief` пост, `gif` видео, `short_video` ролик), настоящий `status` (`published` или `banned`: заблокирована в студии, но по ссылке открывается и собирает просмотры), `url` (адрес для читателя у `published` и `banned`), `created_at` и `published_at`. Выборка `--state published` включает заблокированные и не-статьи; фильтруйте по `type` и `status`. |
| `dzen article show <id\|url> [--format md\|json]` | Статья. В JSON `ad_marked` = `true`, если в тексте есть строка рекламной маркировки («Реклама.» с ИНН или erid); сами строки в `ad_marking`. То же у `draft show`. |
| `dzen article discard-changes <id> [--yes]` | Отменяет неопубликованные правки (`remove-unpublished-changes`). |
| `dzen article delete <id> [--yes]` | Необратимо. Снятия с публикации в Дзене нет. |
| `dzen image upload <file\|url> --to <publication_id>` | Загружает картинку, печатает её ID. `push` делает это сам; команда нужна для отдельных случаев. |

| `dzen comment edit <comment_id> --article <id> --text TEXT\|--stdin` | Правка своего, окно 1 час. |
| `dzen comment delete <comment_id> --article <id> [--yes]` | Удаление. |
| `dzen comment restore <comment_id> --article <id>` | Восстановление. |
| `dzen comment pin\|unpin <comment_id> --article <id>` | Закрепление. |

| `dzen comment report <comment_id> --article <id> --reason R` | Жалоба: `spam_or_fraud`, `obscene`, `inappropriate`. |

| `dzen comment unban <uid> --article <id>` | Разбан. |
| `dzen comment banned [--limit N]` | Список заблокированных. |

### Вход

| Команда | Что делает |
|---|---|
| `dzen auth import [--browser chrome] [--browser-profile NAME] [--profile NAME] [--all]` | Забирает уже авторизованную сессию из Chrome. Браузер не запускает и ничего не спрашивает. `--all` заводит профиль на каждый найденный аккаунт. |
| `dzen auth login [--profile NAME]` | Отдельное видимое окно для входа, нужен TTY. Запускается только явно. |
| `dzen auth list` / `use <profile>` / `status [--live]` / `logout <profile>` | Управление профилями. |

### Архив

Локальные команды не ходят в сеть и не читают учётные данные. Сеть только у `sync`.

| Команда | Что делает |
|---|---|
| `dzen crawl sync <channel> [--max-articles N] [--refresh]` | Публичный канал по адресу с никнеймом. Адреса `/id/<hex>` публичная лента не поддерживает. |
| `dzen crawl sync --mine` | Своё: черновики, запланированные, опубликованные, комментарии. |
| `dzen crawl status` / `search` / `semantic-search` / `embed` / `export-md` | Как в прежнем `dzencrawl`. |
| `dzen crawl sql '<SELECT>'` | Строго read-only, запись отвергается. |

### Служебные

`dzen doctor`, `dzen metadata --json` (`crawlkit.control.v1`, `id: dzen`), `dzen version` и `--version`, `dzen completion bash|zsh|fish`.

## Формат файла статьи

Диалект описан в [отчёте 05, раздел 6](research/05-document-model.md): CommonMark с директивами HTML-комментариями `dzen:empty`, `dzen:gallery`, `dzen:embed`, `dzen:raw`. Живая проверка уточнила отчёт 05: `STRIKETHROUGH`, `depth>0`, H1 и H4 сервер отвергает, поэтому `~~`, вложенные списки и эти заголовки падают локально с кодом 2.

Авторские поля front matter: `title`, `cover`, `snippet`, `comments`, `comments_visibility`, `native_ad`, `comments_title`. Теги на статьях сервер не сохраняет, поэтому поля `tags` нет. Обложкой может быть только картинка из тела статьи: иную Дзен молча отбрасывает, отвечая `OK`, поэтому такой файл отклоняется локально с `validation_cover_not_in_body`. Комментарии выключены ровно тогда, когда они невидимы: если файл меняет только одно из двух полей, CLI приводит в соответствие второе. Служебный блок `dzen:` заполняет CLI: `schema`, `publication_id`, `publisher_id`, `version`, `status`. Если `title` нет, а тело начинается с `# Заголовок`, эта строка становится заголовком. Новый файл без служебных полей просто работает.

Снимок `.dzen/<publication_id>.json` хранит нетронутый `contentState`, `version`, `modTime`, справочник картинок, карту блоков и lock загрузок `sha256 → image_id`. В нём текст черновика, поэтому рядом создаётся `.dzen/.gitignore`.

### Алгоритм push

1. Разобрать файл, применить локальные лимиты и правила fail-closed из отчёта 05.
2. Прочитать документ с сервера, сравнить `version` и `modTime` со снимком. Расхождение: выход с кодом 6, `--force` перезаписывает.
3. Выровнять блоки с базой по каноническому хэшу. Совпавшие блоки уходят из снимка байт в байт, собираются заново только изменённые. Удаление якоря `dzen:raw` показывается в плане отдельной строкой.
4. Загрузить новые картинки, учитывая lock.
5. Отправить `contentState` строкой с плоским `{blocks, entityMap}`, без обёртки `draftJsState`, затем прочитать обратно и обновить снимок.

Если изменений нет, запрос не отправляется: сервер увеличивает `version` даже при пустом сохранении. Сервер не проверяет `version`, вся защита от перезаписи на стороне CLI. Id картинки нельзя переиспользовать в другой публикации. Открытая вкладка редактора может затереть результат; это ограничение описано в help команды.

`push` опубликованной статьи требует подтверждения наравне с `publish`: статья сразу выпадает из ленты до применения правок.

## Ввод и вывод

Stdout отдан данным, stderr сообщениям и прогрессу. Цвет только в TTY. Help и ошибки предлагают следующий шаг.

Успех с `--json`:

```json
{"ok": true, "command": "push", "outcome": "confirmed", "data": {}, "meta": {"profile": "default", "as_of": "2026-11-09T12:00:00Z", "journal_id": null}}
```

Ошибка с `--json`:

```json
{"ok": false, "command": "push", "outcome": "rejected", "error": {"code": "revision_conflict", "message": "...", "detail": "...", "retryable": false, "phase": "preflight", "reconcile_hint": null}, "meta": {"journal_id": null}}
```

`outcome`: `confirmed`, `accepted_pending`, `dry_run_ok`, `rejected`, `outcome_unknown`. Списки отдают `data.items` и `data.next_cursor`. Ошибки сервера очищаются, куки и токены не попадают в `detail`.

## Коды выхода

| Код | Класс | Коды ошибок |
|---|---|---|
| 0 | Успех | `confirmed`, `accepted_pending`, `dry_run_ok` |
| 1 | Внутренняя ошибка | `internal_error` |
| 2 | Использование и локальная валидация, ничего не отправлено | `usage_error`, `validation_*`, `markdown_unsupported` |
| 3 | Аутентификация | `not_authenticated`, `session_expired`, `session_invalid`, `csrf_rejected`, `principal_mismatch` |
| 4 | Нужно действие | `needs_confirmation`, `captcha_required`, `captcha_unsupported`, `captcha_failed` |
| 5 | Отказ сервера | `forbidden`, `not_found`, `remote_validation`, `content_blocked`, `channel_restricted`, `commenter_banned`, `comment_edit_window_closed` |
| 6 | Конфликт | `revision_conflict`, `concurrent_edit_suspected` |
| 7 | Временно, не применено | `network_before_dispatch`, `rate_limited`, `server_unavailable` |
| 8 | Неизвестный исход | `outcome_unknown`, `reconcile_timeout` |
| 9 | Дрейф контракта | `contract_drift`, `unexpected_response_shape` |
| 130 | Прервано до отправки | `interrupted` |

## Безопасность

Политику того, что можно агенту, задаёт скилл `skills/dzen`, а не CLI. CLI даёт механизмы.

- Подтверждение нужно для `publish`, `push` опубликованной, `delete`, `discard-changes` и `ban`. В TTY это запрос. Без TTY или с `--no-input` без `--yes`: выход 4 без отправки.
- `--force` снимает только защиту от конфликта версий. `--yes` снимает только подтверждение. Это разные флаги.
- `--dry-run` не читает сессию, не обращается к сети, не запрашивает CSRF. Разбирает файл, проверяет лимиты, строит тело, показывает план и хэш.
- Мутация отправляется один раз. До границы отправки допустимы повторы с backoff, максимум 3. После границы повторы запрещены, кроме явного отказа, гарантирующего неприменение: один раз при `csrf_rejected`, после решённой капчи, после паузы на 429, один раз при загрузке картинки.
- Граница отправки фиксируется через `httptrace`. Мутации не следуют за редиректами. Заголовки `Idempotency-Key` запрещены: они делают POST повторяемым для `net/http`.
- Намерение пишется в `mutation_journal` до отправки: действие, цель, хэш тела, `version`, время.
- При таймауте, обрыве или прерывании после отправки выполняется ограниченная сверка (паузы 1, 2, 4, 8, 16 с, не более 6 запросов). Без доказательства исход `outcome_unknown`, код 8, повтора нет.
- В контуре комментариев успех это только `status:"ok"`, а не HTTP 200.
- Публикация подтверждается переходом в `status:"published"`. Пока у статьи нет `commonUrl`, исход `accepted_pending`: Дзен ещё обрабатывает её, а публичный адрес появится позже. `--wait` опрашивает с ограничением по времени, `dzen status` проверяет позже.
- В Дзене нет способа вернуть запланированную статью в черновики: установка `delayedPublicationFlagState:"off"` с публикацией выпускает её немедленно. Снять план можно только удалением.

## Аккаунты и сессии

Профиль соответствует одному аккаунту и одному каналу, имя по умолчанию равно логину. В конфиге только несекретные алиасы. Сессия лежит в `~/.dzen/sessions/<profile>/session.json`, каталог `0700`, файл `0600`.

Сессия это компактный набор кук `dzen.ru` и `yandex.ru`, по одному значению на имя: полный дамп получает HTTP 431. Импорт из Chrome сначала пробует CDP, если отладка доступна, иначе читает базу кук профиля и расшифровывает значения ключом через `/usr/bin/security` (один клик «Разрешить всегда», переживает пересборки бинарника). После импорта обязательна проверка принципала через `/editor-api/v2/user`; сессия продвигается атомарно, старая сохраняется при неудаче.

Сессия истекла, а профиль импортирован: CLI один раз молча переимпортирует его из того же профиля Chrome, сверяет принципала и повторяет запрос. Это разрешено и для мутации, потому что 401 означает, что запрос не применён. Иначе выход 3. Обычные команды никогда не запускают браузер.

CSRF берётся свежим на пакет операций из `GET /media-api/csrf-token`.

## Капча

Решается автоматически встроенным адаптером 2Captcha API v2, без внешнего CLI и без запроса пользователю. До 3 попыток на операцию, общий срок 120 с на одно решение, `--no-captcha` отключает. Картинка в комментариях идёт как `ImageToTextTask`. Капча VK ID (`captchaLink` при публикации, `captchaData.captchaUrl` в комментариях) идёт как `VKCaptchaTask`: 2Captcha требует для неё прокси из `DZEN_CAPTCHA_PROXY` или `captcha.credential_process`, ответ уходит в теле как `captcha.vkIdCaptchaSuccessToken` либо в заголовке `captcha-vk-token`. Без прокси исход `captcha_unsupported`. В 2Captcha уходят только данные капчи, ссылка на неё, User-Agent и прокси, никогда куки, текст статьи или учётные данные Дзена. Отказ по капче при публикации уже сохраняет содержимое, поэтому рабочая копия обновляется, чтобы следующая попытка не получила ложный конфликт. Отправка повторяется только потому, что сервер отверг запрос. Ключ: `TWOCAPTCHA_API_KEY`, затем `captcha.credential_process` (Service Vault, JSON `{"version":1,"secret":"...","proxy":"..."}`), затем `~/.config/2captcha/api-key`. Неподдерживаемый тип, нулевой баланс, таймаут и отказ дают `captcha_unsupported` или `captcha_failed`, код 4, и сохраняют уже сделанное.

## Конфигурация

Приоритет: флаги, затем окружение, затем `~/.dzen/config.toml`, затем значения по умолчанию.

Окружение: `DZEN_HOME`, `DZEN_CONFIG`, `DZEN_PROFILE`, `TWOCAPTCHA_API_KEY`, `DZEN_CAPTCHA_PROXY`, `NO_COLOR`.

Данные: `~/.dzen/config.toml`, `dzen.db`, `sessions/`, `assets/`, `articles/`. При первом запуске `~/.dzencrawl` один раз атомарно переносится в `~/.dzen`, затем применяются миграции схемы.

## Архив

`dzen crawl` получает только интерфейс чтения (`Reader`), проверяется тестом на граф импортов: пакет crawl не импортирует код записи. Коллекции: публикации, ревизии, комментарии, авторы комментариев, ассеты. Статистика отложена. Firecrawl удалён: тело берётся из `contentState`.

Схема v2 и правила описаны в [отчёте 03](research/03-data-crawl-boundary.md): lossless raw, ревизии по `content_sha256`, чекпойнт на коллекцию с явным признаком завершения, транзакция страница плюс курсор, идемпотентные upsert, `degraded` как отдельный итог, глобальный лимит 1500 мс на аккаунт и хост. Рабочие копии живут вне архива, `sync` их не трогает. Первыми исправляются дефекты D1–D4 из того же отчёта.

Приватные API стоят за типизированным адаптером. Ограниченный дрейф-зонд сверяет форму ответов и `content-type`; расхождение даёт `contract_drift`, а не догадку.

## Скиллы

`skills/dzen/SKILL.md` для внешней работы задаёт границы агента: всё с черновиками и чтение свободно; комментарии и удаление черновика с указанием цели; публикация, план, правка и удаление опубликованного, бан только после подтверждения пользователя в чате. `.agents/skills/verify-dzen/` для разработки проверяет CLI на реальном канале; аккаунт и ID канала берутся из локального конфига и в репозиторий не попадают.

## Отложено

Статистика и доход; теги статей; снятие отложенной публикации без удаления; закрепление публикаций; подборки; премиум-тарифы; промо и VK Реклама; импорт из других браузеров; переименование GitHub-репозитория; смена типа публикации.

## Не подтверждено вживую

Запись статей, картинки, отложенная публикация, удаление и работа сессии вне браузера проверены на тестовом канале ([отчёт 06](research/06-live-authenticated.md)). Контракты ниже взяты из бандла, реализованы и закрываются в `verify-dzen`: решение VK-капчи (нужен прокси), запись комментариев целиком (нужна статья с готовым `commonUrl`), бан и разбан (нельзя проверять на реальных людях), пагинация списков публикаций, частота автосохранения редактора, привязка сессии к IP. Операция, чей ответ не совпал с контрактом, отвечает `contract_drift` и не гадает.

## Примеры

```bash
dzen auth import                                # забрать вход из Chrome
dzen push article.md --dry-run                  # план без сети
dzen push article.md                            # создать или обновить черновик
dzen pull https://dzen.ru/a/SLUG --dir drafts   # взять на правку
dzen diff drafts/article.md --remote            # что поменялось на сервере
dzen publish drafts/article.md --yes --wait 5m  # опубликовать
dzen publish article.md --at 2026-11-20T09:00:00+03:00 --yes
dzen draft list --json | jq -r '.data.items[].id'
echo "Спасибо!" | dzen comment reply CID --article ID --stdin
dzen crawl sync --mine && dzen crawl search "рюкзак"
```
