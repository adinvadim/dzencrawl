# 05. Модель документа Дзена и round trip Markdown

Статус: исследование, ноябрь 2026. Только чтение. Приватные endpoint'ы здесь это наблюдаемые контракты, а не обещания Дзена.

## Вывод

Тело статьи Дзена это Draft.js `RawContentState` с собственными типами блоков (`atomic:image`, `atomic:embed`, `marker`). Он лежит **JSON-строкой** в `publication.content.articleContent.contentState`. Заголовок, сниппет и обложка хранятся отдельно, в `content.preview`, и в тело не входят. Для CLI это хорошая новость: модель плоская, почти целиком ложится на CommonMark, а то, что не ложится, легко переносить как непрозрачные блоки.

Главная рекомендация: **Markdown это вид на документ, а не его хранилище**. `pull` сохраняет рядом нетронутый снимок `contentState`. `push` выравнивает блоки Markdown с этим снимком, и каждый блок, который пользователь не менял, отправляется обратно **байт в байт** со своим `key`, `data` и диапазонами. Заново собираются только изменённые блоки. Один этот механизм закрывает почти все потери: неподдерживаемые блоки, `UNDERLINE`, `badSeoLink`, пробелы на краях диапазонов, галереи с особыми полями.

Что осталось неизвестным, тоже важно. **Бандл редактора получить не удалось, живого чтения черновика не было**, поэтому всё о семантике сохранения (раздел 4) выведено из стороннего кода и помечено соответственно. До реализации `push` нужен один проверочный прогон на одноразовом черновике (раздел 7).

### Метки достоверности

| Метка | Значение |
|---|---|
| **[Live]** | Observed live: наблюдалось вживую запросом к работающему сервису |
| **[Bundle]** | Derived from bundle: выведено из публичных JS-бандлов Дзена |
| **[HTML]** | Observed in public HTML: публичный SSR/HTML статей или официальная справка |
| **[Inferred]** | Inferred: логический вывод, в том числе из стороннего кода (источник указан) |
| **[Unknown]** | Unknown: установить не удалось |

### Источники и ограничения

**Выборка.** 110 публичных статей (`?output=1`, 3 208 блоков) из лент 10 каналов разной тематики (опрошено 24, у остальных лента пуста или адрес не существует) плюс ссылки с главной страницы. Выборка смещена: `origin` равен `rss` у 53 статей, `platform` у 16, `tg-bot` у 4, не задан у 37. Значит, типы, которые редко используют авторы редактора, могли не попасть. Отсутствие типа в выборке не доказывает его отсутствие в Дзене.

**Блокер: Chrome не авторизован в Дзене** (`isAuthorized:false` на главной). Входить запрещено правилами задачи, поэтому чтение черновиков и трафик редактора недоступны.

**Блокер: бандл редактора.** Приложения названы в enum из `dzen-root` (`article-editor-desktop`, `article-editor-mobile`, `editor`, `brief-editor`, `video-editor`) **[Bundle]**, но их версионированные пути есть только в HTML за авторизацией. Анонимный запрос к `/profile/editor` даёт 302 на SSO **[Live]**, а в индексе Wayback запросы по префиксам `article-editor` и `e` пусты, причём часть других префиксов завершилась таймаутом, так что это не полное доказательство **[Live]**. Перебирать версии на CDN я не стал. Публичный клиент `content/article` тоже не содержит рендера тела (`data-block-type`, `header-two` и `inlineStyleRanges` в нём отсутствуют), значит, тело рендерится на сервере **[Bundle]**.

**Сторонний код**, только как вторичный источник: `vetalione/content_pipeline` (`packages/api/src/services/publishers/dzen-api.ts`, HTTP-клиент публикации) и `fromgate/ProzenExtension` (`reference/zen-api.toml`).

Ничего не создавалось и не менялось: только GET, маршруты создания не открывались, вкладка закрыта. Заметка для краулера: без `--compressed` страницы `?output=1` обрываются на таймауте около 2 МБ, а SSR-данные начинаются примерно с 2,9 МБ; с gzip тот же ответ приходит за 2–3 с **[Live]**.

### Метаданные **[HTML]**

`content.preview` содержит `title` (string), `snippet` (string), `image` (объект картинки, есть у 108 из 110), `blurredPreview` (string) и `galleryPreviewImages` (array).

| Что | Где | Наблюдения |
|---|---|---|
| Заголовок | `preview.title` | Только там. В теле первый блок совпал с заголовком в 4 статьях из 110. Лимит 140 символов, ссылки запрещены (справка **[HTML]**). |
| Подзаголовок | нет поля | Отдельного subtitle не существует **[HTML]**. Роль лида играет первый абзац. |
| Сниппет | `preview.snippet` | Максимум 1000 символов. В 75 из 110 это начало текста тела. Справка: описание «генерируется автоматически». Сторонний клиент при сохранении шлёт `snippetFrozen: true`, что намекает на ручное задание **[Inferred]**. |
| Обложка | `preview.image` | Независима от тела: первая картинка тела в 67 статьях, другая картинка тела в 8, в теле отсутствует в 33, ещё у 2 обложки нет. |

### Тело **[HTML]**

Строка `contentState` разбирается в `{ "draftJsState": { "blocks": [...], "entityMap": {...} }, "mentions": [] }`. Форма одинакова у всех 110 статей, `mentions` всегда пуст.

| Поле блока | Тип | Наблюдения |
|---|---|---|
| `key` | string | Длина 5 (основная масса), 4, 3 или 20. Дубликатов нет. Длина 20 это всегда `marker`, а также блоки у `origin: tg-bot`. |
| `type` | string | Раздел 2 |
| `text` | string | У `atomic:image` это **подпись к картинке** |
| `depth` | int | 0 у всех 3 208 блоков |
| `inlineStyleRanges[]` | `{offset, length, style}` | |
| `entityRanges[]` | `{key: int, offset, length}` | `key` указывает в `entityMap` |
| `data` | object | Пусто у текстовых блоков |

`entityMap` это объект с ключами-строками чисел, запись `{type, mutability, data}`. Ключи **не обязаны быть сплошными**: с разрывами в 32 статьях из 110, минимальный ключ бывает 1, 2, 4. В выборке встречается только `LINK` с `mutability: MUTABLE`.

**Смещения считаются в кодовых точках Unicode, а не в UTF-16** **[HTML]**. Проверка на статьях с эмодзи, где две трактовки расходятся: все 11 ссылок совпадают с текстом `<a>` в отрендеренном HTML только при подсчёте кодовых точек, ни одна при UTF-16. Для inline-стилей та же картина (5 подтверждений, 0 в пользу UTF-16). Это соответствует Draft.js (`UnicodeUtils.strlen` в сериализации) **[Inferred]**. В Go это удобно: `[]rune` даёт правильные смещения.

### Два формата? Да, и третий под вопросом

Первый: `contentState` для хранения и чтения **[HTML]**. Второй: готовый HTML от сервера **[HTML]**, с `p`, `h2`, `h3`, `blockquote`, `ul`, `ol`, `li`, `figure`, `figcaption`, `a`, `b`, `i`, `u`, `br`, `iframe`.

Третий вопрос: **формат записи**. Сторонний клиент отправляет `contentState` как `{blocks, entityMap}` **без обёртки `draftJsState`** **[Inferred]**, а публичный SSR отдаёт обёртку. Принимает ли сервер обе формы и совпадает ли формат чтения в редакторе с публичным, **[Unknown]**. Это первый пункт проверки.

Отдельного поля версии схемы документа в `contentState` нет **[HTML]**.

Детали, которые влияют на реализацию.

`UNDERLINE` в выборке стоит **только на ссылках**: 29 из 29 **[HTML]**. В панели редактора его нет (справка), так что это похоже на наследие старого редактора **[Inferred]**. Отдельный синтаксис не нужен, сквозной проход его сохранит.

Поля `LINK`: `url` есть всегда, `href` отсутствует у 130 из 561 и лишь раз отличается от `url` (хвостовой слэш), изредка встречается служебный `badSeoLink` **[HTML]**. Читать следует `url`, писать оба поля с одним значением **[Inferred]**.

Галерея: `data.image.id` (первая картинка), `data.images[{id}]`, `data.contents` как map imageId → подпись. В 11 из 18 блоков в `contents` есть ещё **буквальный ключ `imageId`** **[HTML]**, вероятно артефакт клиента **[Inferred]**. Блок с `images` длиной 1 тоже встречается (7 раз), поэтому форму нельзя выводить из количества. Лимит галереи 30 картинок (справка).

`data.embedData` различается по типам: у Instagram и YouTube только `type` и `postUrl`, у карточки публикации полный снимок (`publicationId`, `publisherId`, `publisherName`, `publisherAvatar`, `title`, `image`, `publishTime`, `isPremium`, `timeToReadSeconds` и другие) **[HTML]**. Его нельзя пересобрать из URL, поэтому только сквозной проход.

## 3. Картинки

### Загрузка

**[Unknown]** напрямую, бандл редактора недоступен. Известное:

| Факт | Метка |
|---|---|
| Можно загрузить файл с компьютера или дать ссылку на картинку | **[HTML]**, справка |
| Ширина от 300 px, размер до 30 МБ, подпись до 2000 символов, вложений на статью до 100 | **[HTML]**, справка |
| `POST /editor-api/v2/add-image-from-url?publicationId=…&url=…&publisherId=…&clientRid=…`, тело `{}`, в ответе id картинки | **[Inferred]**, `dzen-api.ts` |
| `POST /editor-api/v2/add-image` (multipart); имя поля **[Unknown]** | **[Inferred]**, только комментарий в `dzen-api.ts` |
| Загрузка привязана к `publicationId`, то есть черновик создаётся раньше картинок | **[Inferred]**, там же |
| Заголовки `X-Csrf-Token` из `GET /media-api/csrf-token` (поле `result`), `X-FP-Token`; ошибка `captcha-required-error` | **[Inferred]**, там же |

Важная деталь: сторонний клиент не загружает файлы напрямую, а сначала кладёт их на imgbb и просит Дзен забрать по URL. **Причина неизвестна**, возможно, multipart упирался в антибот-проверки **[Inferred]**. Для CLI multipart предпочтительнее, потому что не утекает на сторонний хостинг, но его придётся проверить. Отправка черновика через чужой публичный хостинг по умолчанию недопустима.

### Идентификатор и URL **[HTML]**

Объект в `images`: `id`, `namespace` (`zen_doc` для статей, `zen-logos` для логотипов), `groupId` (int), `imageName`, `meta` (`mainColor`, `origFormat`), `sizes` (`orig`, `scale_2400`, `scale_1200`, `scale_600`, у части `scale_720`, `scale_540`, `scale_360`, с `width` и `height`).

Форма URL: `https://avatars.dzeninfra.ru/get-<namespace>/<groupId>/<imageName>/<size>`.

`imageName` выглядит как `pub_<24hex>_<imageId>`. Суффикс равен id во всех 336 проверенных случаях. Префикс равен id публикации в 309 случаях, а в 27 это другой идентификатор. Форматы `origFormat`: JPEG, PNG, WEBP, GIF. Запросы размеров `orig`, `scale_1200`, `scale_2400`, `scale_600` отдают 200 и картинку, неизвестный размер отдаёт 404 **[Live]**. Ширина `orig` в выборке от 269 до 3840 px, медиана 1200.

В блоке хранится только `{id}`, размеры и имя лежат в справочнике `images`. Значит, при записи достаточно id **[Inferred]**.

### Как разрешать `![](…)`

| Значение `src` | Поведение `push` |
|---|---|
| Локальный путь (`./img/a.png`) | Проверка существования, формата, ширины не меньше 300, размера до 30 МБ. Загрузка, затем запись в lock по SHA-256. |
| `https://avatars.dzeninfra.ru/get-…/<…>_<id>/<size>`, id есть в базовом снимке | Без загрузки, используется `id`. |
| URL avatars, id **нет** в снимке | Fail closed. Переиспользование чужого id **[Unknown]**, проверка не проводилась. |
| Внешний `https://…` | Импорт только с флагом `--import-remote`. По умолчанию fail closed. |
| `data:`, `http://` | Fail closed. |

При `pull` картинка записывается как URL `.../scale_1200`. Это превью в любом Markdown-просмотрщике, стабильный diff и никаких дополнительных скачиваний. Id извлекается из URL.

Дедупликация: `.dzen/<publication_id>.json` хранит `sha256 → imageId` для текущей публикации. Повторный `push` без изменения файла не загружает картинку снова. Между разными публикациями кэш не используется, пока не проверено, что id переносимы: в выборке 0 из 336 id встретились более чем в одной публикации **[HTML]**.

## 4. Семантика сохранения

Весь раздел под оговоркой: бандла редактора нет. Метки честные.

| Вопрос | Ответ | Метка |
|---|---|---|
| Создание черновика | `POST /editor-api/v2/add-publication` c `{title:"", publisherId, publicationType:"article", fp:""}`, в ответе id | **[Inferred]**, `dzen-api.ts` |
| Сохранение | `POST /editor-api/v2/update-publication-content` | **[Inferred]**, там же |
| Сохранить и опубликовать | `POST /editor-api/v2/update-publication-content-and-publish` | **[Inferred]**, там же |
| Маршруты существуют | Анонимный GET на `add-publication` и `update-publication-content` даёт 405 `MethodNotAllowedException` (работа другого исследователя) | **[Live]** |
| Чтение | `GET /editor-api/v2/get-publication?publisherId=&publicationId=`, `GET /media-api/get-publication?publicationId=`, `GET /editor-api/v3/publications?state=draft&publisherId=&pageSize=` отвечают 401 без сессии, форма ответа неизвестна | **[Live]** |
| Модель записи | **Полная замена документа**: в теле весь `articleContent.contentState` | **[Inferred]**, там же |
| Параметры запроса | `publisherId`, `clientRid` (14 hex) | **[Inferred]**, там же |
| Тело запроса | `id`, `preview{title,snippet,image{id}}`, `snippetFrozen`, `hasNativeAds`, `commentsFlagState`, `delayedPublicationFlagState`, `visibleComments`, `visibilityType`, `premiumTariffs`, `customCommentsTitle`, `articleContent{contentState}`, `tagsInput{tags,detectedTagsShown}`, `fp` | **[Inferred]**, там же |
| Обязательность полей | Неизвестно, какие из них обязательны | **[Unknown]** |
| Оптимистичная блокировка | `publication.version` есть и растёт; сторонний клиент его **не отправляет**, то есть рассчитан на работу без него. Значит, запись, скорее всего, безусловная | **[Inferred]** |
| Ответ при конфликте | Неизвестен | **[Unknown]** |
| Частота автосохранения | Неизвестна | **[Unknown]** |
| Ключи блоков | Генерирует клиент; 5 символов `[a-z0-9]` в стороннем коде и в данных | **[Inferred]**, **[HTML]** |
| `marker` | Сторонний клиент его не шлёт, в опубликованных есть всегда. Похоже, добавляется сервером | **[Inferred]** |
| Ошибки валидации | Форма `{errors:[{type,message}]}` есть у внутренних ошибок | **[Live]** |
| Неизвестные типы блоков | Неизвестно: отвергаются, стираются или сохраняются | **[Unknown]** |

Практические следствия. Запись безусловна, поэтому **защита от перезаписи целиком на стороне CLI**: перед отправкой заново читать документ и сравнивать `version` со снимком. Это не атомарно, окно гонки остаётся, но небольшое. Если статья открыта в браузере, автосохранение редактора может перезаписать результат CLI в любой момент, и наоборот, а значит, в документации нужно честное предупреждение.

У опубликованной статьи правки уходят через статус «Есть неопубликованные правки», а на время правки статья не показывается в ленте (справка **[HTML]**). Публикация также запускает проверку, от минут до часов. Поэтому `publish` всегда отдельная явная команда, а `push` по умолчанию только сохраняет.

## 5. Точность round trip

### Что делает текущий экспорт

`internal/markdown/export.go` и `draftMarkdown` в `internal/dzen/parser.go` сделаны для архива, и как основа записи они не годятся:

| Поведение | Последствие |
|---|---|
| Основной текст берётся из Firecrawl (HTML → Markdown) | Форматирование зависит от стороннего конвертера, идентичность блоков теряется |
| Fallback `draftMarkdown` пропускает блоки с пустым `text` | Исчезают все картинки без подписи, embed'ы и пустые абзацы |
| У картинки с подписью выводится `text` без префикса | Подпись становится обычным абзацем, а картинка пропадает |
| Нет обработки `ordered-list-item` | Нумерованный список превращается в абзацы |
| Игнорируются `inlineStyleRanges` и `entityRanges` | Теряются все ссылки и жирный текст |
| `strings.TrimSpace` | На краях блока срезает и U+00A0, а неразрывные пробелы есть в 57 блоках |
| Нет экранирования | Текст с `*`, `_`, `[` меняет смысл при обратном разборе |
| В файл добавляются `## Комментарии` и метрики в front matter | Тело нельзя отправить обратно, метрики дают шум в diff |
| Имя файла выводится из заголовка | Переименование статьи меняет путь |

Экспорт стоит оставить как есть, для архива он хорош. Для авторинга нужен отдельный конвертер, работающий напрямую с `contentState`.

### Цели

1. **Нетронутое не меняется.** `pull` и затем `push` без правок отправляют семантически идентичный документ, а в идеале CLI вообще ничего не отправляет.
2. **Потеря только явная.** Любая необратимая операция видна в плане до отправки.
3. **Детерминизм.** Один и тот же `contentState` всегда даёт один и тот же Markdown.
4. **Простой путь простой.** Новый файл без служебных полей просто работает.

### Механизм: снимок и сквозной проход

`pull` создаёт `article.md` и `.dzen/<publication_id>.json` с полями: нетронутая строка `contentState`, `version`, `modificationTime`, `images`, карта `key → хэш канонического Markdown блока`, lock загрузок. Снимок содержит текст черновика, так что каталог `.dzen/` по умолчанию добавляется в `.gitignore`.

`push` работает по шагам:

1. Разобрать Markdown в список блоков промежуточного представления (goldmark, CommonMark плюс GFM strikethrough).
2. Перечитать документ с сервера и сравнить `version` со снимком. Несовпадение значит конфликт и остановку.
3. Выровнять блоки с базовыми через LCS по каноническому хэшу.
4. Совпавший блок отправить **из снимка как есть**.
5. Изменённый блок (текст изменился, позиция та же) сохраняет `key`, текст и диапазоны строятся заново, `data` берётся из базы.
6. Новому блоку выдаётся 5-символьный `key` без коллизий с уже использованными.
7. Удаление директивы `dzen:raw` означает намеренное удаление блока и показывается в плане отдельной строкой.
8. Форма обёртки (`draftJsState` и `mentions`) берётся из снимка, `marker` сохраняется.
9. `entityMap` пересобирается и нумеруется заново, ссылки в `entityRanges` переписываются согласованно.

Для неподдерживаемых типов Markdown содержит однострочный якорь с `key`, а само содержимое лежит в снимке:

```markdown
<!-- dzen:raw key="p0ll1" type="atomic:poll" -->
```

Якорь можно передвинуть, это перемещение блока. Если снимка нет, `push` такого файла fail closed. Держать полный JSON прямо в Markdown я не рекомендую: длинный JSON мешает агенту, раздувает diff и провоцирует случайные правки.

### Ловушки (с данными из выборки)

| Ловушка | Данные | Решение |
|---|---|---|
| Пробелы на краю стиля: `** жирный**` по CommonMark не будет выделением | 42 из 327 диапазонов | В канонической форме сдвигать пробел за маркер. Блок без правок всё равно идёт из снимка |
| Стиль внутри слова | 1 из 327 | Использовать только `*`, а не `_` |
| Строки, похожие на разметку (`1. `, `- `, `#`) | 13 блоков `unstyled` | Экранировать, иначе абзац станет списком. Сквозная проверка свойства `parse(serialize(x)) == x` |
| Символы `*`, `_`, `[`, `<`, `\|` в тексте | 11, 21, 8, 1, 17 блоков | Экранировать при выводе |
| Пробелы по краям блока | 154 блока | Канонизация не должна давать ложный diff |
| Неразрывные пробелы | 57 блоков | Сохранять дословно, не применять `TrimSpace` |
| Пустые абзацы как отступы | 48 между блоками | `<!-- dzen:empty -->`; в новых файлах пустые строки ничего не создают |
| Мягкие переносы | 50 блоков | Только `\` в конце строки, два пробела невидимы и съедаются редакторами |
| Обычный перенос строки в абзаце Markdown | | Это пробел, а не `\n`. Канонический вывод не переносит строки, абзац идёт одной строкой |
| Смежные списки одного типа | | В Draft неразличимы, сливаются, как и в Markdown |
| Цитата из нескольких абзацев | соседних `blockquote` в выборке нет | Каждый абзац внутри `>` это отдельный блок `blockquote` |
| Смещения | | Считать в кодовых точках (`[]rune`), покрыть тестом с эмодзи |
| Ссылка внутри стиля | 52 пересечения | Вложенность допустима, вывод строго вложенный, порядок детерминирован |
| Разрывы в `entityMap` | 32 статьи из 110 | Не полагаться на сплошную нумерацию |
| `alt` у картинки | У Дзена поля alt нет (`alt=""` в HTML) | Предупреждение, значение не отправляется. Нельзя тихо превращать его в видимую подпись |

### Как сделать `diff` осмысленным

Нужны два сравнения: локальный файл против базы (что отправится) и база против текущего состояния сервера (что поменялось без нас). Формат это обычный unified diff канонического Markdown, а изменения, которых в тексте не видно, идут отдельным списком:

```text
~ title: "Старый заголовок" -> "Новый заголовок"
~ cover: новый файл ./cover.jpg
- raw p0ll1 atomic:poll (блок будет удалён)
+ image ./img/chart.png (будет загружена, 412 КБ)
```

Канонизация применяется к обеим сторонам, поэтому правка только форматирования не даёт шума. Поля `key` в diff не участвуют.

Критерий готовности: на всём корпусе из 110 статей цепочка `contentState → Markdown → разбор → сборка` без правок даёт JSON, совпадающий с исходным, плюс property-тест на случайных документах.

## 6. Рекомендуемый диалект

Основа: CommonMark, GFM strikethrough. Директивы оформлены HTML-комментариями: это обычный CommonMark, парсеру не нужны расширения, а файл остаётся валидным Markdown.

### Front matter

Авторские поля лежат на верхнем уровне, машинные в `dzen:`. Агент не должен менять `dzen:`.

| Поле | Тип | Обязательно | Соответствие |
|---|---|---|---|
| `title` | string, до 140 символов | Да, либо ведущий `# ` в теле | `preview.title` |
| `cover` | путь или URL avatars | Нет | `preview.image.id` |
| `snippet` | string, до 1000 символов | Нет; если не задан, генерирует Дзен | `preview.snippet`, `snippetFrozen` |
| `tags` | array of string | Нет | `tagsInput.tags` |
| `comments` | `on`, `off` | Нет | `commentsFlagState` |
| `comments_visibility` | `visible`, `invisible`, `subscribe-visible` | Нет | `visibleComments` |
| `native_ad` | bool | Нет | `hasNativeAds` |
| `dzen.schema` | int | Управляется CLI | версия диалекта |
| `dzen.publication_id` | string | Управляется CLI | `publication.id` |
| `dzen.publisher_id` | string | Управляется CLI | `publisherId` |
| `dzen.version` | int | Управляется CLI | версия снимка |
| `dzen.status` | string | Управляется CLI | только для чтения |

Если `title` не задан, а тело начинается с `# Заголовок`, эта строка становится заголовком. Агенты пишут так по привычке, и файл должен просто работать. Любой другой H1 это ошибка.

Метрики (просмотры, дочитывания, лайки) и комментарии в файл автора не попадают.

### Полный синтетический пример

```markdown
---
title: "Как выбрать походный рюкзак"
cover: ./img/cover.jpg
snippet: "Объём, подвеска и вес: на что смотреть при покупке."
tags: [походы, снаряжение]
comments: on
comments_visibility: visible
native_ad: false
dzen:
  schema: 1
  publication_id: "000000000000000000000001"
  publisher_id: "000000000000000000000002"
  version: 12
  status: draft
---

Хороший рюкзак незаметен в пути. Плохой напоминает о себе **на каждом километре**.
```

### Что должно падать, а не деградировать

Формат ошибки: номер строки в файле, код причины, предложение исправления.

**Структура документа**
- Нет заголовка, заголовок длиннее 140 символов или содержит разметку или ссылку.
- H1 в теле (кроме ведущего), а также H4–H6.
- Таблицы, блоки кода, инлайн-код, горизонтальные линии, сырой HTML, неизвестная директива `dzen:*`.
- Вложенные списки, пока прогон не подтвердит поддержку `depth`.
- Картинка внутри абзаца с текстом, в ссылке или в заголовке.
- Ссылка в подписи картинки (подпись это плоский `text` без подтверждённых диапазонов).
- Текст длиннее 100 000 символов, больше 100 вложений, галерея более 30 картинок, подпись длиннее 2000 символов.

**Картинки и ссылки**
- Файл не найден, формат не поддержан, ширина меньше 300 px, размер больше 30 МБ.
- URL avatars с id вне снимка, внешняя картинка без `--import-remote`, `data:`, `http://`.
- Схема ссылки не `http` и не `https`.

**Целостность**
- `dzen:raw` с ключом, которого нет в снимке, или файл с такими якорями без снимка.
- Дублирующийся ключ якоря.
- Изменение `dzen.publication_id` или `dzen.publisher_id` по сравнению со снимком.
- Несовпадение `version` с сервером (конфликт, нужен явный `--force` или повторный `pull`).
- Неизвестный тип блока при `pull` не падает, а становится `dzen:raw`, и CLI сообщает об этом. Падать должен только случай, когда снимок записать не удалось.
- Ответ сервера с неожиданной формой обёртки: не угадывать.

## 7. Что проверить до реализации `push`

Нужна авторизованная сессия и **одноразовый черновик**, созданный вручную, с явного разрешения. Порядок важен, потому что каждая проверка снимает риск для следующих.

1. Прочитать черновик через `get-publication`: совпадает ли форма с публичным `{draftJsState, mentions}`? Есть ли там `version`?
2. Снять из вкладки редактора URL бандла `article-editor-desktop` и извлечь полный список типов блоков, стилей и entity. Это закроет большую часть разделов 2 и 4.
3. Сохранить черновик без изменений и убедиться, что документ не меняется. Принимается ли обёртка, принимается ли плоская форма?
4. Проверить, сохраняется ли блок неизвестного типа, и что сервер делает с `marker`.
5. Проверить `depth > 0`, `STRIKETHROUGH`, подписи с диапазонами.
6. Загрузить картинку через multipart `add-image` и выяснить имя поля и форму ответа.
7. Проверить поведение при устаревшем `version`, если поле отправляется.
8. Узнать, переносимы ли id картинок между публикациями.

Открытые вопросы, которые эта проверка не закроет полностью: выживают ли CLI-записи при открытом редакторе, какова частота автосохранения и как часто будет появляться капча.
